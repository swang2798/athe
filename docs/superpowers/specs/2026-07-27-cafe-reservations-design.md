# At-Home Cafe Reservations — Design

**Date:** 2026-07-27
**Status:** Approved for implementation

## Purpose

Let friends reserve an hourly slot at an at-home cafe from the everydayathe.com
site. Seating is limited, so each hour has a fixed number of seats. A booking
needs only a name and a party size. The system must prevent overbooking, let a
guest look up their booking with a code, and let the host (admin) see and manage
all reservations.

The design is reusable: a future cafe is added by editing one config file and
redeploying — no rewrite.

## First Event

- Date: 2026-08-02
- Hours: 10am–2pm PST → hourly slots 10–11, 11–12, 12–1, 1–2
- Seats per hour: 4
- A booking has a party size of 1–4; the sum of party sizes in an hour cannot
  exceed 4 (one party of 4 fills the hour; four solos also fill it; 2+2 fills
  it; etc.)

## Architecture

```
React page (/cafe/reserve)  ──fetch──►  Cloudflare Worker  ──►  D1 (reservations)
        ▲                                      │
        └──── reads cafeEvents.ts ─────────────┘  (Worker bundles the same config)

Booking returns a short hex code → shown on confirmation + saved to localStorage
→ used for lookup anytime.
```

- **Frontend:** new `ReservePage` (`/cafe/reserve`) and `AdminPage`
  (`/cafe/reserve/admin`), added to the existing CRA + react-router-dom app.
- **Worker:** a small Cloudflare Worker (new `worker/` project in the repo,
  deployed via Wrangler). It is the only thing that touches D1 and it enforces
  the seat cap server-side.
- **Storage:** Cloudflare D1 (SQLite), one `reservations` table.
- **Shared config:** `cafeEvents.ts` is imported by both the page and the
  Worker so slot definitions never diverge.

Rationale: the site already runs on Cloudflare (Pages + R2). A Worker + D1 stays
on the same stack, and the free tier covers friends-and-family traffic. D1 is
the cleanest fit for storing reservations and powering the admin list. A
Durable Object would give stronger concurrency guarantees but is overkill at
this scale.

## Data Model

D1 table:

```sql
CREATE TABLE reservations (
  code       TEXT PRIMARY KEY,   -- 6-char hex, generated by the Worker
  event_date TEXT NOT NULL,      -- "2026-08-02", ties booking to an event
  slot_hour  INTEGER NOT NULL,   -- 10, 11, 12, 13 (start hour, 24h)
  name       TEXT NOT NULL,
  party_size INTEGER NOT NULL,   -- 1–4
  created_at TEXT NOT NULL       -- ISO timestamp
);
CREATE INDEX idx_event_slot ON reservations (event_date, slot_hour);
```

- A slot is identified by `event_date` + `slot_hour`.
- Seats left for a slot = `seatsPerHour − SUM(party_size)` over that date+hour.
- `code` is the primary key and the lookup handle.
- No email, no accounts.

Frontend config (`src/data/cafeEvents.ts`), shared with the Worker:

```ts
export interface CafeEvent {
  date: string;         // "2026-08-02"
  startHour: number;    // 10
  endHour: number;      // 14  (exclusive; last slot is 13–14)
  seatsPerHour: number; // 4
  timezone: string;     // "PST" (display label only)
}

export const cafeEvents: CafeEvent[] = [
  { date: "2026-08-02", startHour: 10, endHour: 14, seatsPerHour: 4, timezone: "PST" },
];
```

The page shows the **next upcoming** event, or a "no cafe scheduled" state if
none. Adding a future cafe = add a row and redeploy.

## Worker Endpoints

All JSON. The Worker imports `cafeEvents` and validates against it.

```
GET  /api/availability?date=2026-08-02
     → { date, slots: [ { hour: 10, seatsLeft: 4 }, { hour: 11, seatsLeft: 2 }, ... ] }

POST /api/reserve
     body: { date, hour, name, partySize }
     → 200 { code, name, partySize, date, hour }
     → 409 { error: "slot full", seatsLeft }
     → 400 on bad input (unknown date/hour, partySize not 1–4, empty name)

GET  /api/booking?code=a3f9c1
     → 200 { code, name, partySize, date, hour }  |  404 if not found

GET    /api/admin/reservations           (header: x-admin-password)
     → 200 { reservations: [ ...all, sorted by date, hour, created_at ] }  |  401
DELETE /api/admin/reservation?code=a3f9c1 (header: x-admin-password)
     → 200 { deleted: true }  |  401 | 404
```

### Overbooking guard

The reserve endpoint re-sums `party_size` for the target date+hour and inserts
only if `sum + partySize ≤ seatsPerHour`, done as a single D1 batch so two
racing bookings can't both take the last seats — one wins, the other gets 409.
Airtight enough at this scale; no Durable Object needed.

### Booking code

6 hex characters (~16M combinations), generated by the Worker. Unguessable in
practice for a small cafe; it is the proof of ownership for lookup. Not
"security"-grade, which is acceptable here.

### CORS & secrets

- Worker allows the site origin (`everydayathe.com`).
- Admin password stored as a Worker secret (`wrangler secret put ADMIN_PASSWORD`),
  never in frontend code or git.
- The Worker has its own URL (Cloudflare route such as `reserve.everydayathe.com`
  or a `*.workers.dev` URL). The frontend calls it via an env-configured base URL.

## Frontend

**Routes** (both new, added to `App.tsx`):

- `/cafe/reserve` — booking page, linked from `/cafe`.
- `/cafe/reserve/admin` — admin list.

**ReservePage** (`src/pages/ReservePage.tsx` + `styles/ReservePage.module.css`):

- Reads next upcoming event from `cafeEvents.ts`; if none → "No cafe scheduled
  right now."
- Header: date, time range, "max 4 guests per hour" note.
- Fetches `/api/availability` on load; renders each hour slot with seats-left.
- Booking form: name (text) + party size (1–4 select); pick a slot; submit
  `POST /api/reserve`.
- Full slots are disabled/greyed. A party larger than a slot's seats-left can't
  select it (client guard; server-enforced regardless).
- On success: confirmation card showing the booking code, saved to
  `localStorage`; refetch availability.
- On 409: "that slot just filled up" + refetch.
- Lookup: a "View my booking" input — enter code → show details. Auto-shows from
  `localStorage` if a code is remembered.

**AdminPage** (`src/pages/AdminPage.tsx`):

- Password prompt → held in memory for the session, sent as `x-admin-password`.
- Table of all reservations grouped by date/slot, party sizes, per-slot total.
- Per-row delete (calls `DELETE`, refetches).

Styling follows the existing cafe aesthetic (`CafePage.module.css`) and the
semantic design tokens introduced in the recent styles refactor.

## Scope

- Book-only. No self-service cancel or edit. Removal is admin-only via delete.
- No email or notifications.
- Single active event shown at a time (next upcoming).

## Testing

- **Worker:** unit tests (vitest + local D1) for seat math, validation (party
  bounds, unknown date/hour, empty name), overbooking → 409, code
  generation/lookup.
- **Frontend:** light tests (`react-scripts test`) for slot-availability
  rendering (full vs. open, party-size guard).
- **Manual:** `wrangler dev` end-to-end before deploy.

## Deploy

- Frontend: existing `npm run build && npm run deploy` (gh-pages).
- Worker: `wrangler deploy`; D1 provisioned via `wrangler d1 create` and schema
  applied via `wrangler d1 execute`. Admin password set via `wrangler secret put`.
